# Event Envelope Contract

Canonical versioned event-envelope schema shared by all services. Verified against source on `main` (issue #22); every subsequent roadmap ticket that touches events references this document.

## 1. The `DomainEvent` interface

Shared interface `com.repertorio.common.event.DomainEvent` (in `shared/common`) declares exactly:

| Method | Type | Meaning |
|--------|------|---------|
| `eventId()` | `UUID` | Producer-generated unique id for this occurrence (see section 3). |
| `occurredAt()` | `Instant` | When the event occurred, set by the producer. |
| `aggregateType()` | `String` | Aggregate name, e.g. `procesion`, `cruceta`. |
| `aggregateId()` | `UUID` | Id of the aggregate the event belongs to. |
| `eventType()` | `String` | Stable discriminator, e.g. `PROCESION_CREATED`. |

Ticket 10 of the active roadmap adds `schemaVersion()` with a temporary default of `1`; the default is **mandatorily removed at Gate 15** so missing metadata cannot be hidden.

## 2. Concrete event records

Every concrete event (e.g. `ProcesionCreatedEvent`, `ProcesionPlanFinalizedEvent`, `CrucetaDefinedEvent`, `HermandadCreatedEvent`) is a Java record implementing `DomainEvent`. Each provides a convenience constructor that generates:

- `eventId = UUID.randomUUID()`
- `occurredAt = Instant.now()`

Examples (verified in source):

| Event | `aggregateType()` | `eventType()` |
|-------|-------------------|---------------|
| `ProcesionCreatedEvent` | `procesion` | `PROCESION_CREATED` |
| `ProcesionPlanFinalizedEvent` | `procesion` | `PROCESION_PLAN_FINALIZED` |
| `CrucetaDefinedEvent` | `cruceta` | `CRUCETA_DEFINED` |

The full event record is serialized to JSON via `ObjectMapper`; that JSON is the outbox payload.

## 3. The envelope `eventId` is producer-generated

**The envelope `eventId` is `UUID.randomUUID()` generated by the producer at event construction. It is never derived from the payload.**

Deterministic hashing is **rejected**: two events with identical payloads that represent different events must not collide (e.g. the same marcha assigned to the same cruceta item twice are distinct occurrences).

### Consumer-side dedup is a separate mechanism

Consumer idempotency for at-least-once delivery uses the **producer-generated envelope `eventId`** as the key in the `processed_event` table — never a value derived from payload bytes. Consumers parse the payload to extract `eventId`, check the table, process, then record the event after success.

Migration status: hermandad's consumer (`IdempotentEventConsumer`) migrated in Ticket 12 (#26); repertorio's procesion consumer (`ProcesionEventProcessor`) migrated in Ticket 13 (#27). No main-code consumer computes a payload hash anymore; new consumers must follow the same pattern.

## 4. Outbox persistence and transport

`OutboxEventEntity` (`shared/common`, table `outbox_event`) stores:

| Column | Content |
|--------|---------|
| `aggregate_type` | `aggregateType()` |
| `aggregate_id` | `aggregateId()` |
| `event_type` | `eventType()` |
| `payload` | `TEXT`, full JSON serialization of the event record |
| `created_at` / `processed_at` / `processed` | Lifecycle timestamps and flag |

The outbox poller runs on `@Scheduled` every 5 seconds and sends each unprocessed row to the `{aggregateType}-events` destination:

- Kafka topic under the `!aws` profile
- SQS queue under the `aws` profile

From Ticket 10 onward the Kafka message key is the `aggregateId`; the outbox row additionally carries `event_id`, `occurred_at`, and `schema_version` (expand/contract migration).

## 5. Delivery semantics

- **At-least-once delivery.** A duplicate delivery after a producer or consumer crash is expected and is absorbed by consumer idempotency (`processed_event` dedup today, envelope `eventId` dedup from Tickets 12-14).
- **No exactly-once claims anywhere.** Never document, assert, or market the pipeline as exactly-once.

## 6. Testable assertions

A reviewer must be able to write a failing test from each assertion:

1. Two events with identical payloads but different occurrences have different `eventId` values.
2. Every event record exposes non-null `eventId`, `occurredAt`, `aggregateType`, `aggregateId`, `eventType`.
3. The envelope `eventId` is never derived from payload bytes (no `nameUUIDFromBytes` on the producer side; a mutation of the payload does not change the `eventId`).
4. The outbox `payload` is valid JSON and contains the envelope fields (`eventId`, `occurredAt`, `aggregateType`, `aggregateId`, `eventType`).
5. `schemaVersion` is present on every event once Ticket 10 lands; Gate 15 removes the default so a missing `schemaVersion` fails validation.
